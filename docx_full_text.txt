Project analysis, technical specification, UI direction and Antigravity master prompt

The supplied project topics spreadsheet lists Project 17 as “Task Scheduler with Deadlines.” Difficulty: Easy. Main data structure: Heap / Priority Queue. Objective: Organize tasks according to deadlines or priority. Suggested operations: add tasks, set deadline/priority, view next task, complete tasks. Expected learning: heap operations and priority-based ordering. Suggested languages: C++, Java, Python.

Submission guidelines in the spreadsheet call for: problem statement and objectives; data-structure selection and justification; algorithm/flowchart; working implementation; sample inputs/outputs; time-complexity analysis; project report and demonstration.

2. Product concept

Product working name: TICKLINE (renameable). Concept: a deadline-aware workbench for students who want to see what deserves attention next, why it is next, and whether their available time is enough. The visual design should feel like a crafted desktop instrument, not a generic AI productivity dashboard.

“Why this task?” explanation card: explain the exact ordering rule and relevant values.

Time-fit indicator: compare duration estimate with the user’s available work window; flag mismatch without claiming to solve scheduling optimally.

Deadline pressure strip: show time remaining as a compact label, not dramatic color overload.

Completion receipt: show task, finished timestamp and queue change after completion.

Keyboard-friendly quick capture and clear empty/loading/error states.

Avoid in the first version

Avoid AI chatbots, AI-generated task plans, motivational quotes, streak gamification, weather widgets, social feeds, decorative analytics, fake collaboration, excessive gradients, meaningless progress rings, and “smart” claims that are not backed by implemented logic. These dilute the data-structure learning objective.

4. Scheduling policy and algorithm design

Recommended deterministic policy: eligible active tasks are ranked by (1) deadline ascending, (2) priority descending, (3) creation timestamp ascending, (4) stable task ID ascending. This makes the deadline the primary key and priority a tie-breaker. If your instructor expects priority-first ordering, expose a policy setting and document both policies. The UI must name the active policy.

A binary min-heap stores a composite key. Convert descending priority into a sortable component (for example, negative numeric priority). Do not rely on heap iteration to show sorted results; repeatedly popping a copy or using a separate sorted projection is needed.

Recommended implementation approach: maintain a task repository as source of truth and rebuild the heap from active tasks after edits, deletes, reopen operations, or policy changes. This is easier to reason about and avoids stale heap entries. For larger scale, use lazy invalidation/version IDs, but it is unnecessary for this mini-project. Demonstrate insertion and removal on the live queue.

Next-task recommendation is not the same as a complete feasible schedule. Tasks may overlap, take longer than estimated, depend on other tasks, or have flexible deadlines. In v1, call it “Next up” or “Queue order,” not an optimal plan.

5. Data model

Task fields: task_id (UUID or stable integer), title, notes, deadline (timezone-aware or explicitly local), estimated_minutes, priority (e.g. 1–5), status (active/completed), created_at, completed_at, updated_at, version.

Suggested persistence: SQLite. Suggested tables: tasks; optionally app_settings for ordering policy and preferences. Store timestamps consistently (UTC preferred) and display in local time. If the implementation simplifies this, state the assumption in the report.

6. Recommended language and stack

Python 3.12+: best balance for fast delivery, readable algorithms, and a credible custom heap implementation.

Streamlit: fast desktop-web UI for a college demonstration. Use carefully designed layout, custom CSS only where supported, and reusable functions.

SQLite: durable local task storage without requiring a hosted database or account.

pytest: test heap invariants, ranking rules, mutations, overdue logic and persistence.

Plotly only if a meaningful queue timeline adds value; avoid adding chart dependencies by default.

Alternative: Java + JavaFX is suitable if your evaluation values object-oriented desktop application development. C++ is suitable if implementation purity is the priority, but building a distinctive polished web UI will take more work. Do not implement the same core in multiple languages.

7. UI/UX direction: “crafted instrument”

Visual concept: an editorial task console inspired by studio equipment, printed timetables and field notebooks. Use warm paper/off-white (#F4F1E9), near-black ink (#20211F), muted graphite, and one restrained vermilion accent (#C84C36). Use hairline separators, typography with a strong display face paired with a highly legible sans-serif, deliberate spacing and asymmetry. Avoid the standard purple/blue AI SaaS gradient, oversized hero text, glassmorphism, generic 3-column feature cards and excessive rounded pills.

Layout: slim left rail for Queue, All tasks, Completed, Heap lab, Settings; compact top strip for current date and active ordering rule; main column with “NEXT UP” task and rationale; adjacent or lower queue list; narrow deadline rail. On smaller screens collapse navigation and stack content.

Use visual hierarchy rather than decoration: deadline text, task title, estimated effort, priority, and rationale should be scannable. Distinguish overdue using label + icon + text, not color alone. Support keyboard focus, readable contrast, useful empty states, and responsive layouts.

9. Complexity analysis to include

Heap peek: O(1).

Heap insertion: O(log n).

Heap extract-min / pop: O(log n).

Heap build from n tasks: O(n) using bottom-up heapify.

Heap search for arbitrary task: O(n) absent an auxiliary index.

Editing a task with simple full rebuild: O(n) rebuild; explain this deliberate simplicity.

Sorted display by sorting active tasks: O(n log n).

Space: O(n) for heap/repository; state any auxiliary maps.

Use measured behavior and the actual chosen implementation. If using heapq plus a map or custom heap, make the complexity discussion match the code. A heap is not a fully sorted collection.

10. Acceptance tests

Equal deadlines resolve by priority, then creation time, then stable ID.

Inserting and popping preserve heap invariant.

Editing deadline or priority changes the queue correctly.

Completing the next task removes it from active queue and persists completion.

Reopening a completed task reinserts it.

Past-deadline tasks are marked overdue without crashing.

Deleting a task does not leave a ghost queue entry.

Reloading app restores tasks and settings.

Invalid fields show actionable errors.

Demo mode produces reproducible ordering.

Show overdue/capacity warning and explain what it does—and does not—claim.

Finish with time complexity and tests.

13. Recommended viva talking points

Why a heap? It supports efficient retrieval of the highest-ranked eligible task.

Why not a BST? Both can support ordering, but a heap is optimized for repeatedly retrieving the root, not arbitrary range queries.

Why a comparator? It formalizes the scheduler’s ordering and tie-break behavior.

Why rebuild after editing? Simpler correctness and no stale entries for a small course project, at O(n) cost.

What is the limitation? The top-ranked task is not necessarily the only feasible or globally optimal scheduling choice.

How would you scale it? Indexed heap, versioned lazy deletion, dependency constraints, and explicit time-slot scheduling—each with added complexity.
